## 3. 奖励（C）

- 核心公式直接用 `src/reward.py::step_reward`，没有改动，λ=0.3。
- 前面加了一层：先用评测的解析器判断合法性，所以"奖励判 −1"和"评测判非法"是同一个判据。
- 插件不用 swift 给的补全文本，而是自己从生成的 token id 解码。原因是 swift 记录的补全文本末尾带着 `<|im_end|>`，而评测时 vLLM 给出的文本没有它。
- 三层核对：
  1. 任务 05 checkpoint-2000 的全部留出集原始输出：n=13,956，0 不一致（其中非法 44 条：候选编号错 37 条、超预算 7 条）。这一步只读已有结果，不涉及训练。
  2. swift 的 qwen3 模板编码出的提示，与评测的提示 id 逐 token 比对：抽 300 个状态，vllm 和 pt 两种编码模式都是 0/300 不一致。
  3. 冒烟训练中 swift 实际记下的奖励，用评测解析器逐条重算：n=832，0 不一致。

## 4. 采样探针（D）：每个状态采 8 条，看奖励有没有差异

做法：从状态池里每格抽 32 个状态，共 192 组；每组按温度 1.0、top_p 1.0 采 8 条。GRPO 只能从"8 条奖励不全相同"的组里学到东西。

| 格（每格 32 组） | 平均奖励 | **8 条奖励全相同的组** | 最好一条比贪心高（均值） | 有某条超过贪心的组 |
|---|---|---|---|---|
| append loose | 1.186 | 28（87.5%） | 0.000 | 0% |
| append mid | 1.163 | 29（90.6%） | 0.016 | 3.1% |
| append tight | 1.186 | 27（84.4%） | 0.007 | 3.1% |
| reselect loose | 0.877 | 22（68.8%） | 0.019 | 3.1% |
| reselect mid | 0.755 | 21（65.6%） | 0.078 | 18.8% |
| reselect tight | 0.870 | 22（68.8%） | 0.090 | 15.6% |
| **合计** | 1.006 | **149/192（77.6%）** | 0.035 | 7.3% |

- 1,536 条采样里只有 2 条非法，都是候选编号错。
- 冒烟训练的 25 个 batch 里，8 条奖励全相同的组平均占 74%，和探针结果一致。

## 5. GRPO 冒烟训练（E）：临时配置，不是正式配置

- **做法：**
  - 先把替身 SFT 的 LoRA 合进基座：在 CPU 上用 fp32 合并，存成 bf16。
  - 在合并后的模型上训一个**新的** LoRA（r16 / α32 / dropout 0.05，all-linear）。这样 KL 约束参照的是 SFT 模型，而不是只会输出非法 JSON 的原始 Qwen3。
  - 合并后的模型和"基座 + LoRA"的贪心输出：n=30，0 不一致。
- **配置：**
  - lr 5e-6，cosine 调度；KL 系数 beta 0.04；
  - 每个 prompt 采 8 条，温度 1.0，top_p 1.0，最多生成 256 token；
  - 每个优化步 4 个 prompt（per-device 4 × 梯度累积 8 = 32 条补全）；
  - vLLM 与训练同卡（colocate），显存占比 0.30；
  - 数据是 120 个训练状态（每格 20 个），跑 25 步。
- **实测：**
  - 每个优化步 40.4 秒（n=23，去掉了第 1 步的 49 秒），25 步共 17 分钟。
  - 显存：torch 记录的峰值 26.1 GiB，其中包含 vLLM 的显存池。整卡峰值 29.2 GB，其中约 1.7 GB 是外部进程。
  - 没有出现 NaN 或 OOM。
  - 每条补全平均约 11.5 个 token，没有被截断的。
  - KL 从 0 升到最高 0.067。
- 奖励曲线不做解读，25 步说明不了任何问题。
- **评测链路检查：** 用评测代码把冒烟 LoRA 加载到合并模型上，在 2 个训练任务上闭环跑通：12 条轨迹、120 个状态，0 条非法输出，所有核对都通过。

都是按冒烟实测线性外推的，单卡 RTX 5880。冒烟时 0 号卡上还有一个约 1.7 GB 的外部进程，利用率约 97%，所以这些只是估计。

| 项目 | 估计时间 |
|---|---|
| 训练状态生成：200 / 400 / 800 个训练任务（每个 × 2 模式 × 3 档） | 0.47 / 0.93 / 1.85 小时（约 1.1 万 / 2.2 万 / 4.4 万个状态） |

上表还没算动态采样。如果打开它，把奖励全相同的组过滤后重采，生成的开销会成倍增加。

## 7. 待定的选择（给 Claude 和用户，不在这里拍板）

1. **起点模型：** v1 的 ckpt-2000，还是任务 06 选出的 v2 checkpoint。探针要在选定的起点上重跑一次（30 个任务，约 10 分钟），因为 v2 的状态分布不一样。
2. **约 3/4 的组学不到东西怎么办：**
   - a. 打开 swift 的 `--dynamic_sample`，把奖励全相同的组过滤后重采；
   - b. 离线先采 8 条，只保留有差异的状态；
   - c. 提高温度。

   相关数据：只追加模式只有 9–16% 的组有差异，重选模式有 31–34%。
3. **模式和预算档的配比：** 只追加模式几乎没有学习信号，可以考虑多放重选模式的状态。但这要先看 v2 的探针结果。
4. **学习率和 beta：** 5e-6 下 25 步，KL 就到了 0.067；正式跑可以考虑 1e-6 到 5e-6。beta 暂用 0.04。
5. **prompt 数量和保存间隔：** 2,000 个 prompt 约 5.6 小时，每个 checkpoint 评测要 0.52 小时。
6. **λ：** 先固定 0.3，0 / 0.2 / 0.5 的消融放到后面。
